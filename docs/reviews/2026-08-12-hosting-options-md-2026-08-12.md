# Adversarial Review — docs/planning/2026-08-12-hosting-options.md

- Date: 2026-08-12
- Artifact type: design
- Reviewer: Codex (model qwen3.8-max-preview, reasoning effort config-default)
- Findings: 3 (Critical 0, High 1, Medium 2, Low 0)

## Summary

The artifact proposes migrating documentation hosting from Vercel to GitHub Pages (legacy build) with a Confluence index for work repos, aiming to enforce custody by making the repo the host. The design correctly identifies plan-based visibility risks but fails to specify the authentication mechanism required for the post-merge verification step to actually perform byte-identity checks on non-public content or during the propagation window.

## Findings

### 1. [High] feasibility · 0.95 confidence — Section 1: Publish flow, Option A

> verify | fetch github.io URL, byte-compare against the committed blob

The design specifies fetching the live GitHub Pages URL to verify byte identity but omits the authentication credential required for this fetch. GitHub Pages sites (even public ones) often require authentication during the build/propagation window, and private-repo Pages (allowed on Pro/Team plans per the artifact's own caveat) strictly require a token with `repo` scope. Without specifying that `publish_doc.py` must inject a PAT or OIDC-derived token into the HTTP request for stage 6, the verification step will fail with 401/404 errors, breaking the 'custody chain' guarantee immediately after merge.

**Recommendation:** In Section 1 under 'Publish flow, Option A', explicitly add a requirement: 'Stage 6 verify must authenticate using a PAT with repo scope (for private repos) or a short-lived installation token, passed via Authorization header, to handle propagation delays and private-site access.' Update Section 4 'setup.py checks' to include validation of this token's availability.

### 2. [Medium] completeness · 0.85 confidence — Section 2: Index hosting, by audience

> Work: a Confluence index page, updated by Actions on merge | ... concurrent runs 409

The artifact acknowledges that concurrent Actions runs updating the Confluence index will result in 409 conflicts but provides no resolution strategy. Since the index is rebuilt 'in the same post-merge step that verifies the doc', parallel merges to different docs in the same repo (or across repos sharing an index) are plausible. Without a defined retry-with-backoff or optimistic locking strategy, these updates will silently fail or leave the index stale, contradicting the goal of making missed updates visible.

**Recommendation:** In Section 2 under 'Index hosting, by audience', add a specific conflict resolution directive for the Work/Confluence option: 'On 409 Conflict, the Action must re-fetch the current page version and retry the update up to N times with exponential backoff; persistent failures must be surfaced as a workflow annotation.'

### 3. [Medium] feasibility · 0.7 confidence — Section 1: The private-repo caveat

> eligibility is verified positively per repo — public, or access-control confirmed — never inferred from 'the repo is private, so it is fine'; and a later visibility or plan change can expose a site, so eligibility is re-checked whenever the index rebuilds.

The design mandates re-checking Pages eligibility 'whenever the index rebuilds' to catch plan/visibility changes. However, the index rebuild is triggered by doc merges or repository_dispatch, not by org-level billing or settings changes. If a repo is downgraded from Enterprise Cloud to Team while no docs are being published, the eligibility check never runs, and the private Pages site remains publicly exposed until the next unrelated doc update triggers a rebuild. The safety mechanism is event-coupled to the wrong trigger.

**Recommendation:** In Section 1 callout 'The private-repo caveat', change 're-checked whenever the index rebuilds' to 're-checked on a scheduled basis (e.g., daily) independent of doc publish events, AND whenever the index rebuilds'. Add a corresponding scheduled workflow to the implementation requirements.
