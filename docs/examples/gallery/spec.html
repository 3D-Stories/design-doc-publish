Halyard webhook endpoint specification

Behavior of the Halyard webhook endpoint, pinned precisely enough to build and test against.

  1. Requirements
  2. Acceptance criteria
  3. Vocabulary
  4. Out of scope

Requirements

  1. R1The endpoint MUST verify the signature before parsing the bodyAn unverified payload is untrusted input and must not reach the parser.
  2. R2The endpoint MUST return 202 for an accepted eventAcceptance means persisted, not processed.
  3. R3The endpoint MUST return 401 for a bad or absent signatureThe body is discarded unread.
  4. R4The endpoint MUST be idempotent on (carrier, event_id)A carrier may redeliver any event any number of times.
  5. R5The endpoint SHOULD respond within 200msCarriers retry aggressively past that.
  6. R6The endpoint MUST NOT call the carrier API synchronouslyThat couples our availability to theirs on the write path.

Acceptance criteria

  1. 1Signature precedes parseProven by a malformed body with a valid signature returning 400, and a malformed body with an invalid signature returning 401.
  2. 2Redelivery is safeThe same event delivered five times yields one row and five 202s.
  3. 3Cross-carrier ids do not collideTwo carriers sending event_id "1" yield two rows.
  4. 4Latency holdsp99 under 200ms at 500 events per second.

Vocabulary

MUST
a conformance requirement; a build that fails it is not this spec
SHOULD
strongly expected; deviation needs a stated reason
event_id
the carrier's own identifier, unique only within that carrier

Out of scope

Ordering. Carriers do not promise it and this endpoint does not impose it. Consumers that need ordering must sort by the carrier's scan timestamp, and must tolerate ties.
